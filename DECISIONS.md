Checkout/Employee/Tool FKs use `on_delete=PROTECT`, not CASCADE — rejected CASCADE because tools/employees are soft-disabled via `is_active`, never hard-deleted, so silent history loss would mean a bug elsewhere.
`Tool.objects.currently_out()` filters via `Exists(Checkout...)` subquery, not `filter(checkouts__returned_at__isnull=True)` — rejected the plain filter because the reverse-FK LEFT JOIN makes `__isnull=True` also match tools with zero checkouts, wrongly including never-checked-out tools.
`Checkout.open()` computes `due_back_at` as `checked_out_at + DEFAULT_LOAN_HOURS` in the model layer, not left for the caller — rejected requiring callers to pass `due_back_at` because the 8-hour default is a business rule, not a view/service concern.
`handle_scan()` returns a plain dict with a `status` key (HTTP status code) and native Python date/datetime values, not an HttpResponse — rejected returning a response object because the service must be testable and reusable without a request/view in the loop.
`handle_scan()` checks tool_inactive/calibration_overdue before current-holder state — rejected checking holder state first because an overdue or retired tool must never re-enter circulation, even if it's mid-checkout when it goes overdue.
`/api/scan/` keeps Django's default CSRF protection rather than `@csrf_exempt` — rejected exempting it because the terminal is a same-origin server-rendered page that can send the CSRF cookie/header like any other Django form.
`board_state()` orders rows soonest-due-first — PLAN.md doesn't specify board ordering; rejected insertion/asset-tag order because the most urgent (or overdue) tools should surface at the top of the screen, not wherever they happen to sort otherwise.
Static files live in a project-root `static/` (via `STATICFILES_DIRS`), not `crib/static/` — matches PLAN.md's structure diagram; rejected the app-local default since this project only has one app anyway.
AWAITING_TOOL shows the raw badge (`Badge: E-1042`), not the resolved employee name — rejected calling the API early to resolve it, since PLAN.md defines no badge-only lookup endpoint and `/api/scan/` only resolves identity together with the tool.
`terminal.js` calls `fetch()` directly (with its own `AbortController` timeout) rather than through `api.js` — acceptable stopgap because `api.js` (offline queue, retry) doesn't exist yet per PLAN.md's build order; will be refactored to route through it once built, with no behavior change.
A queued (offline) scan result uses Bootstrap's `warning` variant on the result banner, a fourth color beyond PLAN.md's green/blue/red — rejected reusing `danger` because a queued scan isn't a rejected scan, and showing it as an error would make operators re-scan and double the eventual queue.
Board's stale indicator is checked on its own 1-second timer, decoupled from the 5-second poll timer — rejected computing staleness only at each poll tick because that would make the 15-second threshold only fire in 5-second increments (effectively 15-20s), and understate how stale the data actually is.
Board went from 5s polling to a Django Channels WebSocket push (deliberately expanding past PLAN.md's original "explicitly out of scope tonight: Django Channels, Redis" cut line) — rejected keeping polling because live-dashboard-over-Channels is itself a target skill to demonstrate, not because polling was broken.
Channel layer is Redis (`channels_redis`) in dev/prod, matching Tayco's actual stack, but tests override it to `channels.layers.InMemoryChannelLayer` via `override_settings` — rejected requiring a real Redis instance for the test suite because that would make `pytest` fail on any machine/CI without Redis running, for a property (pub/sub delivery) the in-memory layer already exercises correctly.
`daphne` must be listed in `INSTALLED_APPS` (before `django.contrib.staticfiles`) for `manage.py runserver` to actually serve over ASGI — `channels` alone silently leaves `runserver` on plain WSGI with no error, which is exactly what happened until caught by checking response headers in browser verification, not by any test.
`_notify_board_update()` swallows any channel-layer exception (e.g. Redis down) instead of raising — rejected letting it propagate because a live-board push failure must never break the actual checkout/return, which is the operation that matters.
Board's WebSocket reconnect uses capped exponential backoff, but also listens for the browser's `online` event to reconnect immediately — rejected pure backoff because blind backoff timing can leave the board disconnected for up to the 10s cap even after connectivity has actually returned; found this via browser-based testing, not by inspection.
